# 执行细节：「推荐标签」与「搜索找岗位」的执行关系

> 本文解释岗位是怎么被找到的：两条供给线（频道线 / 搜索线）如何分工、
> 如何排序、枯竭了怎么办。对应代码：`refresh_pool.py` + `run_pipeline.py`。

## 1. 两条供给线

### 频道线（channel）

- 来源：BOSS 岗位列表页顶部的「**推荐**」标签 + 你账号设置的「**求职意向**」频道标签。
- 做法：打开干净的列表页 → 等标签栏渲染 → **只点击标签，不构造任何搜索 URL**（SPA 重渲染会丢失标签栏，所以每个频道都从干净列表页开始）→ 拟人化滚动 → 抽取卡片。
- 来源标记：`channel:推荐`、`channel:AI产品经理(北京)`。

### 搜索线（search）

- 来源：`搜索页 URL`（关键词 × 城市 × 薪资档位）。
- 做法：直接 navigate 到 `https://www.zhipin.com/web/geek/jobs?query={q}&city={city}&salary={code}`。薪资档位用 URL 参数等效实现（实测下拉菜单的合成点击事件不可靠，URL 参数在页面上显示相同的已选筛选标签）。
- 来源标记：`search:407`（50K以上）、`search:406`（20-50K）。

## 2. 为什么是「双线」而不是只搜索

实测数据（2026-10-14，两轮共 3000+ 条）：

| 线 | 单轮增量 | 结论 |
|---|---|---|
| 频道标签 | 首轮 +13，单轮最高 +26 | 平台会**轮换**标签下的岗位，每重点一轮吐一批新的；网页端滚到底不再加载（「查看更多」只指向 App） |
| 多城市搜索 | 单轮 +331 | 大头。同一天同一批关键词换城市/薪资档，增量是频道线的 **25 倍** |

所以：频道线保证「平台认为你合适的岗位」不漏，搜索线保证量的供给。两者叠加才是稳定来源。

## 3. 流水线模式里的执行顺序（run_pipeline.py）

每个周期（cycle）做两件事，边收边投：

```
周期 N：
  ① 收集 2 块（--collect-per-cycle，默认 2）
     ├─ 频道队列非空？→ 取队首频道标签收一块
     │    ├─ 新增 > 0  → 该频道排回队尾（还有产出，继续重点）
     │    ├─ 新增 = -1 → 标签未渲染/被弹走 → 排回队尾下轮重试
     │    └─ 新增 = 0  → 该频道枯竭，丢弃
     └─ 频道队列空了？→ 从搜索队列取一块
          搜索队列 = 薪资档位顺序（50K以上 → 20-50K），
          档内城市×关键词**随机打乱**（build_search_queue 里 random.shuffle）
     每块之间停 3-7 秒
  ② 发送最多 4 条（--per-cycle，默认 4）
     候选排序：频道岗位优先 → 薪资档位顺序 → priority 词 → 标题短者先
  ③ 周期冷却 15-40 秒，进入下一周期
```

要点：

- **频道枯竭不等于搜索枯竭**：某频道一轮滚动 `+0` 才丢弃，之后不再访问；标签渲染失败记 `-1`，不算枯竭，下轮再试。
- **投递优先吃频道岗位**：`select_candidates` 的排序键第一位就是「来源以 `channel:` 开头」。推荐/意向标签里筛出来的合格岗位永远先投，投完了才轮到搜索线攒的池子。
- **搜索队列投完会重建**：一轮全部城市×关键词×档位跑完后重新 shuffle，第二轮顺序就不同了。

## 4. 单独刷池（refresh_pool.py）

不想跑流水线时，可以只刷池子、之后再统一抓 JD + 发送：

```bash
python3 refresh_pool.py                          # 双线全跑（默认）
python3 refresh_pool.py --mode channel --ch-passes 3   # 只反复重点频道标签
python3 refresh_pool.py --mode search \
    --cities 北京,上海,深圳 \
    --kws "AI产品经理,大模型产品经理"              # 只做搜索
python3 refresh_pool.py --rounds 8 --ch-rounds 10      # 滚得更深（更慢更全）
```

- 搜索线遍历顺序：`for 城市 → for 关键词 → for 薪资档`；频道线：`for 遍数(默认2遍) → for [推荐 + 各意向标签]`。
- 池子与来源标记**增量合并落盘**，绝不覆盖已有岗位；每块收完立即写盘，中断不丢数据。
- 命中风控（`RiskHalt`）立即停止整条刷池，需人工查看页面后再继续。

## 5. 发送侧与两条线的关系（send_greetings.py / run_forever.py）

- `send_greetings.py` 是**单轮**脚本：只投「话术库 `messages.json` 里已有 AI 话术」的岗位，投完正常退出。
- AI 话术是逐条读 JD 现场写的，所以每批投完「看起来像停了」是正常现象。
- `run_forever.py` 守护进程解决这个断点：循环调用发送端——
  - 队列还有话术 → 立即续跑；
  - 队列投完 → 待命，每 `BOSS_WATCH_SLEEP`（默认 60s）探测一次话术库，补写新话术后自动继续；
  - 待命上限 `BOSS_WATCH_MAX_IDLE_MIN`（默认 360 分钟，0=无限）；
  - 平台提示当日上限 → 收工；命中风控/验证 → 收工等人工处理。
- 候选排序（发送端自身入口）：`priority` 词命中优先 → 标题短者先（标题短通常更对口）。
